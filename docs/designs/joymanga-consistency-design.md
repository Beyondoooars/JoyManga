# JoyManga 下载与本地书库一致性设计方案

* **作者：** Guan Fangzhen
* **日期：** 2026-11-16
* **状态：** 审阅稿，尚未实施
* **依据：** [concepts_brief.md](../../concepts_brief.md) 及对当前实现的复核

## 1. 设计目标

本方案解决的不是“文件太大”或“技术栈不够新”，而是三组具体边界：

1. 下载任务的生命周期、章节 CBZ 提交和整本 CBZ 合并可能交错，留下不一致的状态或文件竞争。
2. 本地书库的名称匹配、页面刷新和失败重试没有始终以原对象、原请求和最新状态为依据。
3. 日志、后台失败和命令式弹窗各自承担了部分界面责任，导致重复提示或返回键操作底层页面。

目标是形成一套可逐步落地的小范围设计：保留现有下载、恢复、原子写入和阅读体系，先修正一致性，再根据实际测量决定是否改变存储格式。

### 1.1 必须保留

- Android 漫画下载、断点恢复、仅 Wi-Fi 下载和动态并发调整。
- 本地书库、离线阅读、阅读进度与书签、CBZ 导入和自动整本合并。
- 个人中心资料卡、七列签到日历和签到对账。
- 收藏查看、收藏同步、收藏操作修订号及会话代际保护。
- `DownloadManager`/`DownloadQueue` 分层、任务 `task_id`、前端事件 `revision` 排序、事件缓冲和原子文件提交。
- 阅读器现有阅读方式和底部仅保留进度条的界面。

### 1.2 不在首批设计中

- 更换 Vue、Pinia、Tauri、Rust 或 Android 技术栈。
- 引入路由库、数据库、全局服务层或新的下载框架。
- 重写阅读器、全局 store、`jm_client`、Android 前台服务或通知桥。
- 将阅读进度从 `localStorage` 迁到 Rust 全量文件。
- 删除逐章 CBZ 模式、导出命令或历史配置迁移。
- 在没有基线时承诺性能提升百分比，或建设图片字节预算调度器。

用户允许放弃旧记录、进度和配置迁移，但这只是可选简化。本方案选择保留现有配置迁移、减少变更面；不允许因队列损坏或版本未知而阻止应用启动。

## 2. 当前结构与责任边界

```text
下载命令 / 传输页 / 启动恢复
                │
                ▼
        DownloadManager
        运行期任务与调度许可
                │
                ▼
          DownloadTask
        生命周期 + 执行阶段
          │             │
          ▼             ▼
     DownloadQueue    章节 CBZ 最终提交
     恢复状态与落盘             │
                                ▼
                       ArchiveFinalizeState
                       整本合并单飞与补跑
                                │
                                ▼
                     本地扫描 / 阅读器 / 书库页
```

- `DownloadTaskState` 表示任务生命周期，不等于当前文件操作。
- `TaskStage` 表示执行阶段，不应单独用来解决与整本合并的互斥。
- `DownloadQueue` 的持久化状态必须对应运行期任务；不能只修改界面镜像。
- 整本合并按漫画执行，已有 `running` 和 `rerun` 集合应继续使用。
- 阅读器和书库都以 CBZ 内的身份和章节信息为重要依据，文件名不能成为唯一身份。

## 3. 总体设计

采用“**按漫画协调文件提交，按任务维护生命周期，按请求维护界面代际**”的设计。

| 层次 | 责任 | 本方案新增或调整 |
| --- | --- | --- |
| 漫画级传输协调 | 判断能否开始整本合并、创建或恢复下载 | 扩展现有按漫画归档状态，用短临界区协调登记，不持锁执行 I/O |
| 章节任务 | 下载、校验、打包、暂停、失败、完成 | 打包成功后明确提交完成终态；完成写回后才允许移除任务 |
| 持久化队列 | 保存可恢复任务、丢弃旧任务写回 | 保持 v1 格式，先支持批量写入；保留修订号语义 |
| 本地身份识别 | 将文件归属到漫画和章节 | 整本包以包内漫画 ID 和章节 ID 为准，不再先依赖完整漫画名 |
| 前端刷新 | 将磁盘结果转换为可见书库 | 统一调度、短去抖、失效代际；只有显示书库时自动扫描 |
| 用户反馈 | 展示用户可处理的错误 | 命令错误走命令通道；后台持久化失败走明确状态，不再将所有 ERROR 日志变成通知 |

### 3.1 核心不变量

1. 对同一漫画，整本合并读取并清理来源章节期间，不能有新的下载登记或恢复；章节封包结束前先不移除运行期任务。
2. 新建、恢复与整本合并的“检查—登记”必须是同一协调动作；手动整理也使用同一入口，不能绕过互斥。
3. 章节 CBZ 成功提交后，若收尾竞态已留下 `Paused + Done`，恢复或重启应能完成收尾，而不是因运行期对象被移除而无法继续。普通封包中暂停仍可恢复后续封包。
4. 旧 `task_id` 的写回不能修改新任务；仅图片计数变化不应触发整队列落盘。
5. 书库刷新发生时若又有下载或导入变化，旧扫描结果不能将“已过期”标记错误清除。
6. 重试阅读器或收藏请求时，使用用户刚刚尝试的目标，不使用上一次成功请求或默认页码。
7. 后台失败必须仍有可见承接；降噪不等于吞掉错误。

## 4. 下载与归档设计

### 4.1 漫画级协调，而非全局锁

扩展现有 `ArchiveFinalizeState` 的协调职责，保留其 `running`/`rerun` 和 `FinalizeGuard`。首批**不增加章节提交计数**：当前章节封包位于 `DownloadTask::process` 返回之前，只要运行期任务尚未移除，现有活跃任务判断就能阻止整本合并开始。

需要原子协调的动作有：

- 创建或恢复任务：确认没有整本合并运行，再以 `Pending` 或 `Downloading` 状态登记到运行期映射。
- 整本合并开始：在协调临界区内确认没有活跃下载，再登记 `running`；实际扫描、ZIP 写入和删除均在锁外执行。
- 手动整理、自动整理和归档补跑：全部经过同一个登记入口，不能只修自动路径。
- 任务移除：仅在章节封包已返回、终态已写回内存队列后执行。

短临界区可包含任务映射登记和队列同步写入；不等待网络、图片下载、ZIP 或文件删除。文件写入继续使用现有 `TaskFileWrites` 和 `atomic_fs` 机制。锁顺序统一为“任务映射 → 归档协调锁 → 任务事件锁 → 队列锁”：归档收尾本就会读取任务映射，不能反向持归档锁等待任务映射。实施时按实际调用再次核对。

**为什么不只增加一个 `is_running` 检查：**检查之后、任务开始之前仍可能发生归档。协调必须覆盖登记，否则只是缩短竞态窗口。

**为什么不用全局读写锁包住下载：**会把无关漫画和耗时 I/O 串行化，也容易与网络策略锁、任务事件锁形成新的锁顺序问题。

### 4.2 章节打包完成与取消

普通下载、校验阶段仍允许暂停和取消。章节 CBZ 已成功提交后，以 `event_lock` 内的单一收尾动作清理失败记录、写入 `Done + Completed` 并更新队列；此动作可覆盖并发产生的 `Paused`，但不能覆盖 `Cancelled` 或 `Failed`。

- 打包成功且恰在最终迁移前暂停：最终显示已完成，不再留下“运行期已移除、点继续却找不到任务”的 `Paused`。普通打包期间暂停会使下载 future 暂停轮询，恢复后继续封包，不能把它误写成必然留下坏状态。
- 打包失败：进入已有的 `Failed`，保留可诊断错误及可恢复文件。
- 取消在收尾登记前取得事件锁：沿用 `Cancelled` 优先和文件写入门控；不重新触发整本合并。若 CBZ 已经物理提交，它仍由书库身份扫描认回，不回滚、不静默重下；取消记录不伪称文件不存在。
- 收尾先登记 `Completed`：后续取消按钮不再把完成任务改为已取消。

启动、备份导入和事务恢复共用同一个 `Done` 处理规则：`Done` 条目不重新下载，保留可见历史并调度一次既有归档意图补跑；不能只把条目从队列删掉，导致“已封包但未合并”在崩溃后永远不整合。它代表旧版本的封包成功点；未来若改变 `Done` 的写入时机，必须同步修改这个判断。

这个取舍意味着收尾瞬间的暂停请求可能最终看到“已完成”。相比让一个已生成的 CBZ 对应不可恢复的暂停任务，这个状态更贴近磁盘事实；若要求封包期间立即暂停，必须另行定义中断 ZIP、保留半成品和重新校验的协议，不在本批处理。

### 4.3 与整本合并相遇时

- 恢复或创建时整本合并已经运行：拒绝本次操作并说明原因，原暂停任务仍可稍后继续。
- 活跃任务已经登记：整本合并不开始，章节封包结束并写回完成状态后，再按既有调度收集新快照。
- 合并不是“遇到忙碌就永久丢弃”：`rerun` 和 `FinalizeGuard` 继续负责后续补跑，不能以一次空结果清除归档意图。
- 书库删除已有独立归档检查；其“先检查、后取消并删除”的更广事务不在本批扩展。首批先关闭下载登记与归档之间的竞态，并在实施稿列为单独风险，不宣称所有文件操作已串行化。

### 4.4 队列设计：先合并写入，不改格式

首批保留 `DownloadTaskSnapshot` 和 v1 JSON，避免同时改变状态机和恢复协议。

1. 批量创建：先验证章节及现有任务，构造待接受条目；一次持久化成功后再登记并启动新任务。已在下载或暂停的章节按统一结果分类跳过，不重复创建。
2. 启动恢复：批量构造恢复任务和新的任务身份，一次保存后再启动；单个坏条目可明确标为失败，其他合法任务不被拖垮。
3. 计费网络暂停：收集状态实际发生变化的任务，一次提交队列，再发布事件。不能让旧 worker 的迟到写回覆盖新任务，也不能在锁内发送前端事件。
4. 保存失败：不得启动尚未持久化的新任务；批量入队的回滚不得删除先前已有任务。后续更新的内存状态可保留为 dirty，等待下次保存重试，但不能伪装成已持久化；恢复/暂停失败必须进入可见的持久化健康状态。
5. 任务修订：后端现有迟到写回保护只有 `task_id`；队列分配的 `revision` 用于前端事件排序，worker 快照固定为 0。首批先统一任务事件锁内的快照发布，保留单调 revision；只有取得同一 worker 旧快照覆盖新状态的具体失败样例后，才单独实现完整 revision 前置校验。
6. 启动容错：队列和归档意图的内容级问题——未知版本、损坏 JSON 或多个原子写恢复备份——不得阻止主窗口创建。尝试保留原文件副本后以空状态启动；改名失败时不能继续用原路径覆盖它，应切换到独立运行路径并提示。备份导入和事务恢复仍把未知版本作为该次命令错误返回；所有消费者使用同一活动路径。
7. 批量下载分类：已存在的 `Pending`、`Downloading`、`Paused` 属于跳过，不应当作失败中断剩余章节；真正的创建或落盘失败聚合并明确返回。部分成功不得被描述为整批失败。

**验收不是“写入一次就算完成”：**还要证明每个被接受任务的 `task_id`、状态、恢复信息与运行期对象一致，重复任务没有被覆盖。

## 5. 本地书库与身份识别

### 5.1 整本包以包内身份为准

`update_chapter_infos_fields` 当前先以完整、未截断的漫画名筛选整本包。调整为：

1. 只检查当前漫画已有的候选目录和当前平铺书库根目录，不递归读取无关目录。
2. 对候选 CBZ 读取有限大小的元数据和现有整本包身份信息。
3. 只有包内漫画 ID 等于当前漫画，且包含目标 `chapter_id` 时，才将整本包标记为该章来源。
4. 保留旧章节的既有匹配方式作为兼容路径，但不能让旧名称规则覆盖更可靠的身份结果。
5. 合并目标命名继续共用同一文件名生成函数；遇到同名其他漫画时，仍按现有身份检查回退或拒绝，不覆盖外来文件。

这不要求每次读取所有图片。身份检查复用现有 ZIP 中央目录、元数据大小上限和错误处理；无法识别的候选文件仍按原诊断路径处理。

### 5.2 书库刷新协调

将“是否需要刷新”“是否允许自动刷新”“结果是否可提交”分开：

- **可见性：**只有顶层为书库且子页也是书库时，进入或事件才自动刷新；传输页不自动扫描。
- **触发来源：**页面进入、下载完成、归档结束、导入、删除、配置目录变化都进入同一调度入口。
- **调度：**连续事件短去抖，取最后一次；手动导入/删除后的明确刷新可以立即执行。
- **代际：**每次请求记录开始时的失效代际和请求 ID。只有最新请求能提交列表；若扫描期间失效代际已变化，则丢弃旧结果、保持 `stale`，可见时安排后续扫描，不能显示后又假装它是最新。
- **错误：**失败保持 `stale`，手动操作和可见页显示错误；后台事件不能反复弹同一提示。
- **诊断：**复用最近一次有效扫描摘要，不因页面生命周期再次触发同一组扫描。

不直接共享一个在途 Promise 来“解决一切重复”：它不能区分返回期间发生的新变化。可以协调调度，但不能牺牲失效语义。

## 6. 阅读、收藏与配置

### 6.1 阅读器重试

`loadChapter(comicId, chapterId, page)` 在清空当前章节前保存完整请求参数。失败按钮调用无参数的 `retryChapter()`，读取最近一次实际尝试，而不是只读取 `activeReaderTarget` 的两个 ID。

成功加载后仍按实际总页数夹紧页码；只有成功得到非空章节内容时才保存进度。失败、空图片和已被新请求取代的结果不得把原进度写为第 1 页。章节切换和阅读器关闭继续使用现有 generation 守卫。

### 6.2 收藏请求参数

保留 `folderIdSelected`、`sortSelected`、`pageSelected` 表示最后一次成功查询，另存最近一次失败请求的目标参数供重试使用；失败期间不伪造筛选选中态或部分更新列表。

- 翻页、切换收藏夹或排序失败后，重试使用同一失败请求。
- 自动 stale 刷新和“同步收藏夹”也刷新当前目标。
- 切换账号仍重置查询和使旧请求失效。
- 不改动 `recordFavorite` 的修订号比较、登录状态和收藏操作协调。

### 6.3 配置版本

保留当前 v1→v2 迁移。`Config::default` 与 `commit_locked` 统一使用 `CONFIG_SCHEMA_VERSION`；对外提交的 `schemaVersion` 仍由后端管理，前端不能任意指定。

未来若升级 v3，必须增加逐级迁移，不能让 v2 落入旧版无版本兜底。当前启动保存仍可能回写未来版本并丢失未知字段；本批只修正当前版本被写成 v1，不宣称已经提供未来版本安全。删除迁移和未来版本的保留/拒绝回写策略都不是本批目标。

## 7. 反馈、日志与返回键

### 7.1 用户提示与日志分流

- `initLogListener` 只维护日志记录，不再接受通知对象，也不再将所有 ERROR 转为常驻通知。
- 用户直接发起的操作继续由 `CommandError` 和 `formatCommandError` 显示一次错误。
- 归档失败继续使用现有 `ComicArchiveEvent` 和 `archiveFailures`，确保对应页面实际展示。
- 队列保存失败和归档意图保存失败增加窄的领域事件，以短时、可去重的消息提示“状态可能未保存”；成功保存后允许下一次故障重新提示。若采用传输页持续状态，必须同时提供非传输页可见的提示，不能把错误藏在用户当前看不到的页面。详情进入诊断日志。
- 设置中的等级文案明确指文件日志。只有拆分通知与日志通道后，才调整导出过滤，不能误删后台故障信号。
- 清理日志存在实际失败时返回错误，不显示全部成功。

JS 异常持久化、白屏/WebView 失联诊断属于后续独立事项，不在本批新增 Rust 日志桥。

### 7.2 命令式确认框接入返回机制

提供轻量的确认框包装，复用 `registerBackHandler` 和组件激活生命周期：

1. 弹窗存在时，以高于底层页面的优先级处理 Android 返回和 Escape。
2. 返回键走与“取消”相同的真实回调，再销毁弹窗；不能只 `destroy()`，否则等待布尔结果的 Promise 可能不结束。
3. 取消、遮罩、Escape、关闭按钮共用幂等完成逻辑，原回调和返回值语义保持。
4. 确认按钮的异步失败可以继续阻止关闭；不能为了包装而改变原确认流程。
5. 页面失活或卸载时注销该页弹窗的返回处理，并按既有取消语义结束等待中的 Promise；不能让隐藏页面永久吞掉返回键。

不引入路由库，不改变阅读器翻页键盘监听。

## 8. 后续条件性设计

### 8.1 队列 v2：按漫画去重

只有在真实长篇漫画、多任务和大书库上取得基线后，才决定是否将完整 `Comic` 从每个任务中抽为按 `comicId` 共享的记录。CBZ 内完整元数据不随队列精简而缩减。

若启动时遇到未知版本，应尝试保留备份、给出明确提示并以空队列启动；重命名备份失败也要记录后继续。不能把“不做迁移”实现成 setup 失败。恢复任务必须能再次取得完整漫画信息，不能只保存界面展示字段。

### 8.2 文件级书库解析缓存

先减少无意义刷新。仍需要优化时，以规范化路径、长度、修改时间及书库根目录为键复用未变化条目；导入记录、已移除记录、损坏文件诊断和归档提交必须参与失效判断。文件指纹冲突时重新解析，不用缓存结果掩盖损坏。

### 8.3 大图片

阅读端可先展示真实的“字节超限/像素超限/无法解码”，不再一律称文件损坏。是否让下载接受、跳过或拒绝这些页面，需由产品语义和真实样本决定。没有 OOM 测量前，不新增复杂字节预算。

### 8.4 Android 生命周期

先记录 WebView 销毁、服务存活、通知更新和取消操作的真机日志，再决定是否需要改变通知桥。不能凭推测把服务或通知重写为 JNI/Rust 直控。

## 9. 方案权衡

| 选择 | 收益 | 代价与限制 |
| --- | --- | --- |
| 扩展按漫画登记协调 | 关闭创建、恢复与归档之间的检查—登记窗口 | 需要集中核对锁顺序和手动归档入口 |
| 封包成功后完成终态优先于暂停 | 消除“显示暂停、实际完成且无法恢复”的冲突 | 收尾瞬间暂停最终看到完成；已提交 CBZ 不被取消回滚 |
| 保留 v1 队列并批量写 | 改善重复 I/O，变更可独立回退 | 不消除完整 `Comic` 的结构冗余 |
| 身份优先于文件名 | 长标题和云端改名不再使整本包失联 | 候选身份读取仍需控制次数和错误成本 |
| 统一书库调度 | 减少重复扫描并保留最新状态 | 增加失效代际和调度测试责任 |
| 移除通用 ERROR 通知 | 消除重复、内部日志外露和常驻提示 | 必须先为后台持久化失败提供可见承接 |
| 不大规模拆模块 | 保留成熟恢复与事件防护，降低回归面 | 大文件的维护问题不会因本方案自动消失 |

## 10. 设计完成条件

设计审阅应确认：

- 下载、恢复、整本合并和章节提交的协调范围没有遗漏入口。
- 暂停/取消在章节封包阶段的产品语义可接受。
- 收藏、签到和阅读器界面没有被借重构删减。
- 首批不改存储格式，后续改造均有测量或产品决策门槛。
- 各批次的验收能区分代码事实、待执行测试和未实测性能。

具体文件、先后顺序、测试场景和回退方式见 [实施方案](joymanga-consistency-implementation.md)。
